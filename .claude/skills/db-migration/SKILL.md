# PostgreSQL migrations

Source requirements: `init.md` §4 (versioned migrations), §5 (guarantees 3, 5, 7, 8), §6.3–6.5.

## Before starting

1. Confirm the migration tool defined in an ADR (`docs/adr/`). If there is no ADR yet, **stop and
   propose** one (e.g. golang-migrate, goose, tern) using the `adr` skill.
2. Find the latest existing version and follow the tool's naming pattern.

## Rules

- Every migration has **up and down**. The down must actually revert (and be tested).
- Never edit a migration that has been applied/committed: create a new one.
- One logical change per migration; descriptive names (`create_wallets`, `ledger_immutability_trigger`).
- Explicit SQL; nothing implicitly generated by an ORM.
- Monetary types: `BIGINT` in minor units **or** `NUMERIC(p,2)` — per the Money ADR.
  Currency as `CHAR(3)` with `CHECK (currency ~ '^[A-Z]{3}$')`. Never `REAL`/`DOUBLE PRECISION`/`MONEY`.
- Timestamps: `TIMESTAMPTZ`.
- Enumerated states and kinds: `CHECK (status IN (...))` or `ENUM` — justify the choice.

## Invariants that must exist in the database

| Invariant | Suggested mechanism |
| --- | --- |
| Balance never negative | `CHECK (balance >= 0)` |
| One wallet per `(player_id, currency)` | `UNIQUE (player_id, currency)` |
| Version starts at 1 and increases | `CHECK (version >= 1)`; version-conditioned update or row lock |
| External transaction unique per provider | partial `UNIQUE (provider_id, external_transaction_id)` for external rows |
| Unique idempotency key | `UNIQUE` within the scope defined by the ADR |
| Internal vs external | `CHECK` requiring/forbidding external columns by origin (`OPENING` has no provider, round...) |
| Single `OPENING` per wallet | partial unique index `WHERE kind = 'OPENING'` |
| One successful reversal per kind and reference | partial unique index on `(reference_id, kind) WHERE status = 'PROCESSED'` |
| Unique ledger `(wallet_id, transaction_id)` | `UNIQUE` |
| Consistent ledger | `CHECK (balance_after = balance_before + amount)` / `- amount` by direction; `amount > 0` |
| Append-only ledger | `BEFORE UPDATE OR DELETE` trigger raising an exception **and** `REVOKE UPDATE, DELETE` from the app role; consider `TRUNCATE` |
| Unique inbox | `UNIQUE (consumer_name, message_id)` |
| Outbox with stable identity | `event_id UUID PRIMARY KEY`; index for `WHERE published_at IS NULL ORDER BY next_attempt_at` |

## Concurrency in the schema

- Indexes supporting `SELECT ... FOR UPDATE [SKIP LOCKED]` for the outbox, the pending-reference worker
  and `PENDING` resumption.
- Avoid full-table locks in migrations that run while the application is live.
- No global sequence/table used as a mutex.

## Roles

- Consider separating the migration role (owner) from the application role (no `UPDATE`/`DELETE` on the
  ledger). Document it in the ADR and README.

## Verification

- Integration tests (`go-testing` skill) must prove: migrations go up and down from scratch; each
  constraint rejects the corresponding invalid data; `UPDATE`/`DELETE` on the ledger fail.
- Update `docs/requirements/traceability.md` with the evidence (migration file + test).
- Document apply and rollback in `README.md`.
